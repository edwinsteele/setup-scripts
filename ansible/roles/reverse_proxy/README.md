# reverse_proxy

Runs nginx on `viking` as an HTTP-only (LAN, no TLS) reverse proxy in front
of the other services already running on the box, fronting each one with a
friendlier hostname instead of `viking.home.wordspeak.org:<port>`:

- `viking.home.wordspeak.org` - landing page linking to each service below
- `homeassistant.home.wordspeak.org` -> Home Assistant (`127.0.0.1:8123`)
- `fuel.home.wordspeak.org` -> fuel-price-signal workbench
  (`fuel_signal_workbench_host:fuel_signal_workbench_port`)
- `tv.home.wordspeak.org` -> Tvheadend (`127.0.0.1:{{ tvheadend_http_port }}`)

Each of those services keeps its own directly-reachable port and firewalld
rule (untouched by this role) - this just adds nginx in front on port 80.
Tvheadend's HTSP port (`tvheadend_htsp_port`, used by raw HTS clients like
Kodi, not HTTP) is deliberately not proxied here.

## DNS

The hostnames above need to resolve to `viking`'s LAN address - this role
doesn't manage DNS itself. On this network that's `unbound_local_data_content`
in the private `local_setup-scripts` overlay repo's
`ansible/roles/firewall/vars/local_address_vars.yml` (generated by
`generate_local_address_files.py`), which adds them as extra `local-data` A
record names alongside `viking` itself - not true CNAMEs, but resolves the
same way in practice, matching the pattern already used for e.g.
`nicholas-ipad` aliasing `nics-pot-plant`'s IP.

## Why HTTP only, not HTTPS

LAN-only traffic behind the firewall - a self-signed cert would need every
client to click through a browser warning on every visit, or manual trust
pinning, for no real security benefit on a trusted network segment.

## Home Assistant needs a one-time manual trust step

Fronting Home Assistant through this proxy makes it return `400 Bad
Request` to everything until HA is told to trust the proxy. This is *not*
configurable through `configuration.yaml` any more on current HA (verified
against 2026.8.0, `homeassistant/components/http/config.py`): the
`http.use_x_forwarded_for`/`trusted_proxies` YAML keys are migrated into an
internal storage-backed config store exactly once (on whichever boot first
sees a `http:` YAML block, or none at all), and every boot after that
silently ignores YAML for this component and logs a
`yaml_still_present_after_migration` repair issue instead - that migration
had already happened on this box before this role ever ran, with no
`http:` block present, so there's no way back into YAML for it. Trusting
the proxy now has to happen through HA's own UI flow (the same
`http/config` / `http/config/promote` trial-config mechanism as its
auto-detected "reverse proxy in front of Home Assistant" repair card):
open Settings > System > Network (or follow the Repair notification that
appears once this proxy sends it a real request) and trust
`127.0.0.1`/`::1`. One-time step, same category as Tvheadend's DVB channel
scan in `roles/tvheadend`'s README - not something this role can do for
you non-interactively without a logged-in session.

## Why no `default_server`

`/etc/nginx/nginx.conf` (from the `nginx` package) already ships its own
`default_server` block for port 80. Rather than fight that, this role's
server blocks match on explicit `server_name` only - requests to
`viking`'s bare IP or any other unmatched Host header still hit the stock
nginx welcome page, which is harmless.
